## 三、逐项分析：哪些是"真需要"，哪些是"可清理"

### 🔴 大头 1：vmmemWSL — 1920 MB（13.4%）

**是什么**：WSL2 虚拟机的内存占用。你的 Podman 容器
（itsaplan 的 postgres/minio/api/web 等 6 个）都跑在里面。

**CPU 累计 0.0s** —— 因为它通过 hypervisor 计费，不看 Windows 的 CPU 列。

**判定：不能随便杀**，杀了 itsaplan 全停。但**可以限制上限**：
- 你的 `.wslconfig` 里写的是 `memory=6GB`，当前实际用了 1.9 GB，没超。
- 如果 itsaplan 不再需要，停掉容器后这块会自然降下来。

### 🟡 大头 2：svchost — 1814 MB（97 个实例！）

**是什么**：Windows 系统服务的通用宿主进程，**97 个实例**分摊了 1.8 GB。
单个不大，但数量极多。CPU 累计仅 6.8s —— 基本是静止的。

**判定：系统必需，不能手动杀**（杀错一个会导致系统功能失效）。
97 个是 Windows 11 的正常状态，不用管。

### 🟢 大头 3：DeepSeek Harness — 1724 MB（6 个实例）

**是什么**：当前这个 AI 工具本身。CPU 累计 1338s —— **它是唯一真正在干活的**。

**6 个实例**说明：Electron 主进程 + 渲染进程 + GPU 进程 + 工具子进程等。
1.7 GB 对一个跑着 MCP、多插件、长时间会话的 AI 工具来说**正常偏高但不异常**。

**判定：这是你正在用的工具，不能杀。** 但如果你同时开了多个 DSH 窗口，
关掉不用的能省几百 MB。

### 🔴 大头 4：msedgewebview2 — 1276 MB（24 个实例）★ 最值得清理

**是什么**：Chromium 内核的嵌入式网页组件，被各种应用调用。
我查了父进程：
- **clash-verge.exe**（你的代理工具）→ 有 webview
- **SearchHost.exe**（Windows 搜索）→ 有 webview
- 其余 22 个是webview 自己的子进程链

**CPU 累计 38s，启动才 0.2 小时前** —— 说明是最近刚起来的一堆后台渲染进程。

**判定：这里有优化空间。**
- 24 个实例里有大量是webview 的子进程（父进程也是 webview），
  这是正常的进程树，但 1.27 GB 偏高。
- **能做的**：关掉不用的、带 webview 的应用（比如 clash-verge 的面板、
  Windows 搜索的网页功能）。但**不要手动一个个杀**，会被父进程重新拉起。

## 四、明确可清理的无用项（按收益排序）

| 项 | 内存 | 风险 | 做法 |
|---|---|---|---|
| **Podman Desktop GUI** | 680 MB | 低 | 如果只用 `podman` 命令行，退出 GUI 即可，容器不受影响 |
| **NVIDIA Overlay** | 504 MB | 低 | NVIDIA 控制面板 → 关闭"游戏内覆盖" |
| **wetype_update** | 337 MB | 低 | 禁用开机自启（输入法本体保留，只禁更新器）|

## 五点五、深挖发现：wetype_update 是隐藏的第二大头 ★

进一步追溯 webview 进程树，发现 **msedgewebview2 的 24 个实例来源**：

| 根父进程 | webview 数量 |
|---|---|
| **wetype_update.exe** | **12 个** ← 最大来源 |
| clash-verge.exe | 6 个 |
| SearchHost.exe | 6 个 |

**wetype_update（腾讯微克输入法更新器）真实占用**：

| 组成 | 内存 |
|---|---|
| 本体 | 319 MB |
| 它拉起的 12 个 webview | 635 MB |
| **合计** | **954 MB** ← 隐藏的第二大头 |

之前只看进程名聚合，把它算成 337 MB，**严重低估**。算上它拉起的 webview，
它是仅次于 WSL、svchost、DSH 的第四大头。

它的父进程追溯到 **DeepSeek Harness**，但我搜了 DSH 插件源码和所有 profile 配置，
**都没有 wetype 的显式引用**。所以"DSH 插件主动调用"只是推测，未证实。
更可能是：DSH 的某次输入触发了输入法，输入法再拉起更新器，进程树显示为 DSH 后代。
**这一项标注为"不确定"，不要据此去改 DSH 配置。**

同时确认：**python 进程是 `kernel_server.py`（记忆系统核心服务），不能杀。**

## 六、重要更正：强杀无效（实测）

我尝试直接 `Stop-Process` 关掉 NVIDIA Overlay 和 wetype_update，
**两个都被父进程立即重新拉起**（5→5，1→1）。查了进程树才找到真相：

| 进程 | 父进程 | 真相 |
|---|---|---|
| wetype_update | **DeepSeek Harness.exe** | 不是输入法自启，是 **DSH 的插件在调用它**（可能是输入法集成功能）。杀掉 DSH 会立刻拉起 |
| NVIDIA Overlay | **nvcontainer.exe** | NVIDIA 容器服务自动拉起，必须去 NVIDIA App 设置里关 |

**所以"直接杀进程"这条路走不通，必须改源头设置。**

## 七、正确的关闭方法（从源头）

### 1. NVIDIA Overlay（-504 MB）
打开 **NVIDIA App → 设置（齿轮）→ 功能/游戏内覆盖 → 关闭"游戏内覆盖"**。
或直接禁用自启任务：
```powershell
Disable-ScheduledTask -TaskName "NVIDIA App SelfUpdate_{B2FE1952-0186-46C3-BAEC-A80AA35AC5B8}"
```
（注意：这只是自更新任务，关闭覆盖要在 NVIDIA App 界面里操作）

### 2. wetype_update（-337 MB）
父进程是 DSH，说明是某个 DSH 插件在用它。需要：
- 检查 DSH 插件配置里有没有输入法相关集成，关掉
- 或接受它（337 MB 不算大，且是 DSH 功能的一部分）

### 3. Podman Desktop GUI（-680 MB）
**最简单有效**：直接退出 Podman Desktop 程序（点 X 关掉）。
容器跑在 Podman machine（WSL）里，不受 GUI 影响。
这是**唯一可以立刻、安全省下 680 MB** 的操作。

### 4. msedgewebview2（-几百 MB）
关掉 clash-verge 的面板窗口、不用 Windows 搜索的网页功能。
别手动杀进程（会被父进程拉起）。

## 八、一句话总结

**没有单个流氓程序，是"WSL容器 1.9G + 系统服务 1.8G + DSH 1.7G + webview 1.3G"四项叠加吃掉了 47%。**

**能立刻安全省的**：
1. 关掉 Podman Desktop GUI（**-680 MB**）—— 容器不受影响
2. wetype_update + 12 webview 共 **954 MB**，但父进程虽指向 DSH、
   源码/配置里却找不到引用（未证实），**先别急着动 DSH 配置**。
   更稳妥的做法：在 WeType 输入法设置里关掉"自动更新/云同步"，观察是否还拉起。

**最大隐藏问题**：wetype_update 表面只占 337 MB，实际连它拉起的 12 个 webview
一共吃掉 **954 MB**，是内存紧张的重要推手。根源在 DSH 插件（父进程是 DSH），
需要在 DSH 插件配置里关，而不是杀进程。

其余项要么系统必需（svchost/MsMpEng），要么被父进程自动拉起
（NVIDIA Overlay 必须去 NVIDIA App 设置关），要么是你正在用的工具（DSH 本体、kernel_server）。

切勿盲目杀进程 —— 实测证明会被重新拉起，白费力气。
