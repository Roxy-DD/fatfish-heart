# 局域网其他设备访问不了 — 诊断与方案

更新时间：2026-11-20

## 已确认的事实（主机侧全绿）

| 检查 | 结果 | 说明 |
|---|---|---|
| Caddy 绑定地址 | `0.0.0.0:443` | ✅ 不是 127.0.0.1 |
| 本机用 LAN IP 连 | `172.20.10.5:443` → **True** | ✅ 主机自己能连 |
| 服务响应 | `/login` → **200** | ✅ 服务正常 |
| 防火墙规则 | 3 条显式 Allow，`Profile: Any`，远程 Any | ✅ 正确 |
| Hyper-V 防火墙 | `DefaultInboundAction: Allow` | ✅ 已放行 |
| 网络类型 | WSL = **Private** | ✅ 不是 Public 拦截 |
| 第三方杀软 | 无 | ✅ 排除 |
| 容器→宿主 | 通 | ✅ 反向路径正常 |

**结论：主机侧一切正常，问题在「外部设备 → 主机」这一段。**

## 关键纠错（前一个 AI 的判断有误）

它说"本地能打开说明 Caddy 绑在 127.0.0.1，必须改监听地址"——**这个推断错误**。

实测：
```
docker port caddy
  443/tcp -> 0.0.0.0:443     ← 已经是 0.0.0.0
Test-NetConnection 172.20.10.5 -Port 443  → True   ← 用 LAN IP 也能连
```
所以不需要改 Caddyfile 的 `:443` → `0.0.0.0:443`，本来就是对的。

另外，`Get-NetTCPConnection -LocalPort 443` 返回空**不是异常**：
mirrored 模式下端口由 `com.docker.backend` 代理，不体现在常规监听表。
判断依据应该用 `docker port`，不是 netstat。

## 最可能的原因：WSL mirrored 模式的跨设备入站限制

`.wslconfig` 当前是 `networkingMode=mirrored`。

mirrored 模式共享 Windows 的 IP 栈，**本机访问完全正常**（这也是为什么本机能开），
但**跨物理设备的入站连接**在这个组合下存在已知问题：
- Docker Desktop 的端口代理绑定在 Windows 主机上
- mirrored 模式下 WSL 与 Windows 共用网络栈，入站包的路由可能不落到 Docker 的监听上

## 验证方法（需要另一台设备配合）

在**另一台电脑**（172.20.10.3）上执行：

```powershell
# 1. 先测纯 TCP（排除 TLS 干扰）
Test-NetConnection -ComputerName 172.20.10.5 -Port 443

# 2. 测 80 端口（同理）
Test-NetConnection -ComputerName 172.20.10.5 -Port 80

# 3. 如果 443 不通但 80 通，说明特定端口被拦
```

**结果判断：**

| 结果 | 含义 | 方案 |
|---|---|---|
| 443 和 80 都不通 | mirrored 模式的跨设备入站失效 | 方案 A 或 B |
| 80 通、443 不通 | 443 被某种规则拦截 | 方案 C |
| 都通 | 那就能访问了 | 直接打开浏览器 |

## 方案 A：切回 NAT 模式（最可靠，推荐）

NAT 模式下 Docker 的端口映射是经过验证的稳定路径。

### 步骤

```powershell
# 1. 改 .wslconfig
notepad $env:USERPROFILE\.wslconfig
```

把 `networkingMode=mirrored` 改成注释掉（或删掉那一行）：

```ini
[wsl2]
memory=6GB
processors=6
swap=2GB

# networkingMode=mirrored   ← 注释掉，回到默认 NAT
dnsTunneling=true
autoProxy=true
localhostForwarding=true

[experimental]
autoMemoryReclaim=gradual
```

```powershell
# 2. 重启 WSL 和 Docker
wsl --shutdown
# 然后重启 Docker Desktop（托盘退出再开）

# 3. 重启容器
cd deploy\caddy; docker compose restart
cd ..\itsaplan; docker compose -f docker-compose.yml -f docker-compose.override.yml restart

# 4. 验证（主机上）
docker port caddy
# 应显示 0.0.0.0:443
```

NAT 模式下额外可能需要：如果局域网还是不通，加一次性端口转发

```powershell
# 管理员 PowerShell
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=443 connectaddress=127.0.0.1 connectport=443
netsh interface portproxy add v4tov4 listenaddress=0.0.0.0 listenport=80  connectaddress=127.0.0.1 connectport=80
```

## 方案 B：Caddy 用 host 网络（绕开端口代理层）

已经准备好的文件：`deploy/caddy/docker-compose.host.yml`

```powershell
cd deploy\caddy
docker compose -f docker-compose.host.yml up -d
```

⚠ 代价：host 模式下容器不能用 Docker DNS，Caddyfile 里的
`itsaplan-api:3000` / `itsaplan-web:3001` 解析不到。
需要改成宿主机可达的地址，并且给 itsaplan 的 api/web 做端口映射。

**这个方案要改 Caddyfile 的反代目标，比方案 A 复杂。**

## 方案 C：只针对 443 单独排查

如果 80 通但 443 不通：

```powershell
# 检查是否有其他程序/规则占用或拦截 443
netsh advfirewall firewall show rule name=all | findstr /C:"443"
Get-NetFirewallPortFilter | Where-Object { $_.LocalPort -eq 443 }
```

## 我的建议

**先切方案 A（NAT 模式）**。理由：
1. NAT 是 Docker Desktop 的默认和主流路径，跨设备访问最稳
2. 你的痛点（动态 IP）已经有了 `set_lan_ip.py` 工具，不算大问题
3. mirrored 虽然是微软新特性，但在"跨设备 + Docker Desktop"这个组合上不够可靠

切换后如果还不行，我们再上方案 B。
