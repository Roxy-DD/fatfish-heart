# 新应用接入模板 —— 以后任何 Docker 应用都照这个套

> RustDesk 本身不部署（你直接局域网用），这里只作为**占位示例**，
> 演示"一个新 Docker 应用要接入 Caddy 基础设施，需要改哪些地方、按什么顺序操作"。
> 以后不管接什么应用（Gitea、Jellyfin、笔记服务……），流程完全一样。

---

## 一、整体接入模型（记住这张图）

```
用户浏览器
   │ http://172.20.10.100/<应用路径>
   ▼
Caddy 容器（唯一 80 入口，基础设施层）
   │ 通过 proxy 外部网络，用容器名解析
   ▼
<应用> 容器（自己的 docker-compose，挂 proxy 网络）
```

**接入一个应用 = 三件事**：
1. 应用 compose 挂到 `proxy` 网络
2. Caddyfile 加一段反代规则
3. reload Caddy

---

## 二、标准接入流程（通用，4 步）

### 第 1 步：应用的 docker-compose 加 proxy 网络

在任何新应用的 `docker-compose.yml` 里：

```yaml
services:
  <应用服务名>:
    container_name: <应用唯一名>      # 关键：跨项目唯一，避免 DNS 冲突
    networks:
      - proxy        # 给 Caddy 反代用
      - default      # 保留应用自己的内部网络（数据库等）
    # 不需要 ports 映射到宿主机（统一走 Caddy 80）
    # 调试时可临时开 ports，正常运行时注释掉

networks:
  proxy:
    external: true   # 用之前 docker network create proxy 建的网络
```

**要点**：
- `container_name` 必须全局唯一（itsaplan 用了 `itsaplan-web`/`itsaplan-api`）
- `external: true` 表示网络由 compose 外统一管理
- 应用内部服务（如数据库）留在 default 网络，不挂 proxy（安全）

### 第 2 步：Caddyfile 加反代规则

在 `deploy/caddy/Caddyfile` 的 `:80 { ... }` 块里加一段：

```caddyfile
    # ---- <应用名> ----
    # 情况 A：独占路径前缀（推荐，多个应用靠路径区分）
    handle /<应用路径>/* {
        # 如果应用本来就知道自己在 /<应用路径> 下，不用去掉前缀：
        reverse_proxy <应用容器名>:<容器内端口> {
            header_up X-Real-IP {remote_host}
        }
    }
    # 如果应用不知道自己在子路径下（大多数应用），用 handle_path 去掉前缀：
    # handle_path /<应用路径>/* {
    #     reverse_proxy <应用容器名>:<容器内端口>
    # }
```

或独占整个域名/二级路径时另起 site block（有真实域名时）：
```caddyfile
<应用>.example.com {
    reverse_proxy <应用容器名>:<容器内端口>
}
```

**要点**：
- 端口写**容器内监听端口**，不是宿主机映射端口
- 用 `handle_path` 会自动去掉路径前缀（`itsaplan` 的 `/api` 就是这么做的）
- `handle` 块之间互斥，按 matcher 长度自动排序，不用手动调顺序

### 第 3 步：启动应用 + reload Caddy

```powershell
# 启动新应用（在应用自己的目录）
docker compose up -d

# reload Caddy（不用重启容器）
docker exec caddy caddy reload --config /etc/caddy/Caddyfile
```

### 第 4 步：验证

```powershell
# Caddy 能否解析到应用容器名（关键！）
docker exec caddy ping -c 1 <应用容器名>

# 访问测试
curl http://172.20.10.100/<应用路径>
```

## 三、占位示例：如果以后要接 RustDesk 的 Web 客户端

（RustDesk 本体你不部署，直接用局域网。这里只演示"假设它要接进来"该怎么写——
以后换成别的 HTTP 应用，结构完全一样）

### 应用侧 compose（示例，不执行）
```yaml
services:
  some-app:
    container_name: some-app          # 唯一名
    image: some/image:latest
    networks:
      - proxy
      - default
    # 不开 ports，统一走 Caddy

networks:
  proxy:
    external: true
```

### Caddyfile（示例，不执行）
```caddyfile
:80 {
    # itsaplan 的现有规则（保留）...

    # 新应用：路径 /app1
    handle /app1/* {
        reverse_proxy some-app:8080 {
            header_up X-Real-IP {remote_host}
            header_up X-Forwarded-For {remote_host}
        }
    }

    # 兜底：itsaplan web
    handle {
        reverse_proxy itsaplan-web:3001
    }
}
```

**关键点**：`handle` 块互斥且按路径长度排序，`/app1/*` 会优先于兜底 `/`，
所以新应用不会抢掉 itsaplan 的首页。

## 四、踩坑清单（接入新应用前必看）

| 坑 | 现象 | 解法 |
|---|---|---|
| 容器名冲突 | Caddy 反代到错误容器 | `container_name` 全局唯一 |
| 端口写错 | `dial tcp: no such host` 或 connection refused | 写容器内端口，不是宿主映射端口 |
| 没挂 proxy 网络 | Caddy 解析不到容器名 | 应用 compose 里 `networks: proxy + external: true` |
| 路径前缀没处理 | 应用 404（它不知道自己在 /app1 下）| 用 `handle_path` 去掉前缀 |
| 改了 Caddyfile 没生效 | 还是旧路由 | `docker exec caddy caddy reload` |
| 应用有 WebSocket | 连接不上 | Caddy 自动处理 Upgrade，一般不用额外配置 |
| HTTPS 需求 | 浏览器不安全警告 | 纯局域网用 `tls internal` + 每台导根证书；有域名自动签 |

## 五、快速参考卡片

```powershell
# 建共享网络（只需一次）
docker network create proxy

# 起基础设施
cd deploy\caddy && docker compose up -d

# 接入新应用的三步
# 1. 改应用 compose：加 networks proxy + container_name
# 2. 改 Caddyfile：加 handle/handle_path 规则
# 3. docker exec caddy caddy reload --config /etc/caddy/Caddyfile

# 排查
docker exec caddy ping <容器名>                    # DNS 通不通
docker exec caddy caddy validate --config /etc/caddy/Caddyfile   # 配置语法
docker logs caddy                                   # 看日志
```
