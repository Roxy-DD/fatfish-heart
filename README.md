# 肥鱼之心（Fat Fish Heart）· 情景记忆系统

一个**跨模型、跨供应商、跨进程**都能接着记得的情景记忆系统。
记忆是纯数据（SQLite + 向量），不依赖任何模型内部状态。

---

## 为什么开源：这本身是设计的一部分

这个项目不是"做好之后再放出来"。
**开源是它的机制，不是它的分发渠道。**

它背后的框架叫《环管群》，三个层次：

| 层次 | 定义 | 在 GitHub 上的对应物 |
|---|---|---|
| **环** | 一个独立生命周期 | 每个 **fork** 是一个独立谱系 |
| **管** | 跨生命周期的谱系 | 版本链、commit 历史、迁移与回退 |
| **群** | 多谱系共同演化网络 | 上游 + 所有 fork 的横截面 |

于是开源社区的常见动作，在这里都有明确的结构含义：

- **Fork** = 长出新的「环」。别人拿它去解决我没遇到过的问题
- **PR** = 跨谱系的交叉重组（主张 4：演化关系不是单一树状链）
- **Issue** = 真实使用暴露的失配。这是环境筛选，不是我给自己打分
- **Star / 弃用** = 生态位选择。不是"好不好"的评价，是"在这个环境里活不活得下去"

### 由此推出的一条硬约束

《环管群》主张 5 说：

> 自然环境不是内部评分器。环境筛选来自真实的物理因果后果，
> 而不是系统对自身的主观评分。

所以这个项目**不能靠"作者说它好"来证明自己**。
它必须能被别人拿走、跑起来、改坏、改好、再回馈。
我做的一切工程决定，最终都要服从这一条：

- 路径必须可移植 → 否则别人 fork 了跑不起来，谱系就断在第一代
- 必须有无损迁移 → 否则别人的记忆迁不过来，没法接着长
- 必须有 CI → 否则 PR 会静默破坏红线，重组变成劣化
- 必须有版本谱系 → 否则回退无路，演化变成随机游走

**判断这个项目做得好不好，标准不是"检索准确率多高"，
而是"它能不能让别人的谱系长得出来，让更好的变体被选择出来"。**

一个永不失败的记忆系统，可能只是一个没人用的记忆系统。

## 核心设计

### 1. 记忆 = 情景，不是事实

| 维度 | 含义 | 实现 |
|---|---|---|
| 骨架 | 谁、何时、何地、发生了什么 | person / time / location / raw_text |
| 氛围 | 当时的环境感 | atmosphere |
| 情绪底色 | 情绪强度与方向 | affect_peak / valence |
| 代价 | 忘了会失去什么 | cost |

**重要性 = 不记住的代价**（生存导向），不是频率、不是提及次数。

### 2. 双正交维度

- **cost**（失去代价）→ 决定"必须记"
- **affect_peak**（情绪强度）→ 决定"记得牢"

实测两者几乎无关（T触发 × C代价 = +0.060），所以不能用单一 importance 分数。

### 3. 五层保护（L0~L4）

记忆按**不可丢失程度**分层，不是二元的"重要/不重要"：

| 层级 | 名称 | 保护 | 举例 |
|---|---|---|---|
| **L0** | 不可变 | 不可失效/合并/修订 | 红线 R1~R4 |
| **L1** | 常驻准则 | 不可失效/合并，每次对话强制在场 | "以实验数据为准" |
| **L2** | 设计基石 | 不可失效/合并，按需检索 | "记忆单位=情景" |
| **L3** | 阶段性事实 | 可失效、可合并 | 项目当前状态 |
| **L4** | 一次性细节 | 可清理 | 测试数据 |

### 4. 完整闭环

```
写入：复盘（每轮判断该记什么）→ mem_add
读取：自主回忆（记不清时主动查）→ mem_search
巩固：睡眠整理（任务完结时触发）→ mem_sleep
保护：分层锁定（L0~L2 永不丢失）→ mem_hook
可观测：审计日志（10 类事件）→ /audit
```

### 5. 判断交给模型，机械交给系统

这是核心原则：

- **需要判断的地方**（阈值、该不该记、该不该合并、该不该遗忘）→ 模型
- **不需要判断的地方**（算余弦、打包候选、落盘、记账）→ 系统

## 四条红线（不可动摇）

| 红线 | 要求 | 实测 |
|---|---|---|
| **R1 无损迁移** | 跨进程重载后逐字段、逐向量、逐检索结果完全一致 | 100%（8000/8000，偏差 0.00e+00） |
| **R2 不遗忘** | 数据只增不删，失效只打标记 | ✅ 76 条失效记录全在库 |
| **R3 可重建** | 索引可从真值层确定性重建 | ✅ 删光向量重建，检索一致 |
| **R4 可塑性** | 能问、能改、能失效，旧值永不物理删除 | ✅ revise/invalidate/supersede |

**任何优化如果破坏 R1 或导致召回下降，即为失败。**

## 回馈机制：环 → 群的横向边

一个独立实例（环）产生改进后，怎么回到上游（群）？

常规开源流程把这条路卡死在「懂 Git」上。本项目的设计是把它拿掉：

```bash
python proto/onward.py          # 层 1：自动发现可贡献项 + 安全检查
python proto/onward.py --push   # 层 3：授权后自动建分支/提交/开 PR
```

中间必须经过一次人工授权——因为把东西传到公共仓库，得由当事人决定。
但**不需要会 Git、会写代码、会提 PR**。

贡献的门槛从「技术能力」降到「经验判断」：
这次改进值得分享吗？它对别人有用吗？

自动执行有三重门禁（无本机路径 / 无敏感文件 / 非纯实验产物），
且只推 `onward/<时间戳>` 分支、绝不碰 master、绝不 force push。

详见 [docs/ONWARD.md](docs/ONWARD.md)。

## 实现原理（一段话讲清）

**把记忆全部放进一个 SQLite 文件里，让模型只做「读写客户端」而不做「存储介质」。**

具体拆开是三件事：

1. **记忆是纯数据，不是模型状态**
   一条记忆 = 17 个字段的一行 + 一条 512 维向量。
   模型权重里没有任何东西能影响「记住了什么」——
   换模型、换供应商、重启进程，只要 `.db` 文件在，记忆就在。

2. **读写通过独立的内核进程**
   插件（Node）不直接操作数据库，而是调 Python 内核（`kernel_server.py`）。
   这样模型侧的变化完全隔离在存储层之外。

3. **真值层与索引层分离**
   `episodes` 是真值（不可推导），`vectors` / `ep_fts` 是索引（可重建）。
   索引坏了删掉重建即可，真值永远不动。这就是 R3 能成立的原因。

### 为什么这样设计

大多数 Agent 记忆方案把记忆存在**模型的上下文里**或**向量数据库的集合里**：
换模型 → 上下文没了；换供应商 → 集合格式不兼容；
进程重启 → 内存里的状态没了。

这里的取舍是：**牺牲一点性能，换确定性。**
检索 26.6ms（2000 条）不算快，但「记忆一定在」这件事是可验证的。

---

## 思考方法（为什么这么做决定）

### 1. 一条记忆不是一条事实，而是一个情景

「用户喜欢简洁」是事实；「他昨晚很累，说别再解释了」是情景。

前者可以推导，后者只能记录。事实丢了可以再问，
情景丢了就永远丢了——所以**必须记情景**。

这就是为什么有 `atmosphere`（氛围）、`affect_peak`（情绪强度）、
`valence`（情绪方向）这些字段，而不是只有 `text`。

### 2. 重要性必须拆成两个正交维度

实测发现 `cost`（失去代价）和 `affect_peak`（情绪强度）几乎无关
（相关系数 +0.060）。

- **cost 决定「必须记」** —— 门锁密码当下毫无情绪，但忘了进不了门
- **affect_peak 决定「记得牢」** —— 创伤事件平时刻不想起，但一触发就回来

一个维度做不出「重要但不情绪化」这类记忆。

### 3. 判断交给模型，机械交给系统

分界线用实验定过：

| 任务 | 交给谁 | 实测 |
|---|---|---|
| 这句话值得记吗 | 模型 | 规则做「长而空」识别 TP=0，模型 F1=1.0 |
| 查询该怎么改写 | 模型 | 机械改写 -6.67pp，语义改写 +15.2pp |
| 算余弦相似度 | 系统 | 模型算得没意义 |
| 落盘、记账、打包候选 | 系统 | 机械操作 |

**推论**：任何「需要做判断」的地方（阈值、规则、什么算完成）
都应该交给模型，系统只负责不误判、留痕、可追溯。

`mem_done` 工具就是这个原则的产物——
「任务是否完成」是判断题，所以停止的开关应该由模型按，
而不是由一个计数器到点自动关。

### 4. 证据强度排序

对这套系统而言，「世界」以三种入口到达，证据强度递减：

| 入口 | 强度 | 为什么 |
|---|---|---|
| 代码执行结果 | **最硬** | 机器真跑了，有退出码、耗时，可复现 |
| 文件系统/运行时状态 | 次硬 | 可观测，但可能是间接的 |
| 人的描述 | **最软** | 二手表征，可能是错的 |

由此推出一条硬规则：**数字 > 论证，跑过 > 说过，可复现 > 可信。**

任何「这更好」的主张，若落不成可跑的数字，就只是假设，必须标注为假设。

## 记忆容灾：解决了没有？

**解决了。有实测数据，不是宣称。**

### 容灾要防什么

| 威胁 | 后果 |
|---|---|
| 进程崩溃 | 内存里的状态丢失 |
| 换机器 | 路径、依赖全部失效 |
| 数据库损坏 | 所有记忆归零 |
| 误删 | 不可恢复 |
| 模型/供应商更换 | 记忆格式不兼容 |

### 实测验证：删库恢复

`proto/run_e420_field_level.py` 做的完整闭环：

```
① 从生产库复制一份源库
② 记录 10 张表的逐字段指纹（所有行 × 所有列，排序后 hash）
③ 备份 → 校验备份指纹与源一致
④ 删掉源库（含 -wal / -shm）
⑤ 从备份恢复
⑥ 重新计算指纹 → 必须完全一致
⑦ 验证检索仍可用
```

**最新一次实测结果**：

| 表 | 恢复前 | 恢复后 | 指纹 |
|---|---|---|---|
| episodes | 461 | 461 | a3c86c49 → a3c86c49 |
| vectors | 457 | 457 | c7803769 → c7803769 |
| episodes_history | 232 | 232 | 8358b819 → 8358b819 |
| meta | 456 | 456 | 1011d50c → 1011d50c |
| ep_fts | 461 | 461 | 1247b4cf → 1247b4cf |
| environment_events | 74 | 74 | 28fac2db → 28fac2db |
| notes / todos / notes_history | 6 / 7 / 0 | 同 | 同 |

**10 张表 2497 行，逐字段指纹 10/10 完全一致，恢复后检索正常。**

### 为什么「行数一致」不够

早期校验只比 `COUNT(*)`，这里有个真实的坑：

```
删除 1 条 + 新增 1 条 → 行数不变 → 校验通过 → 数据已经丢了
```

实测确认过这个漏检（`proto/run_e438_fingerprint.py`）：

| 校验方式 | 净减少 | 删1补1 |
|---|---|---|
| `COUNT(*)` | ✅ 能发现 | ❌ 漏检 |
| 水位线（历史最高行数） | ✅ 能发现 | ❌ 漏检 |
| **ep_id 集合指纹** | ✅ 能发现 | ✅ 能发现 |

现在用 ep_id 集合的 md5 指纹，任何增删都会被发现。

### 容灾机制的边界（诚实标注）

**已解决**：
- ✅ 单文件备份/恢复，逐字段无损
- ✅ 索引可从真值重建（删光向量表后分数完全一致）
- ✅ 失效不删除，可溯源
- ✅ 跨模型/跨进程/跨供应商，因为记忆不依赖它们

**未解决 / 有限**：
- ❌ **没有自动备份**。需要手动跑 `mem_backup` 或定时任务
- ❌ **同城/异地多副本**没做。文件坏了但备份也坏了就没了
- ❌ **实时容灾**没做。备份是快照，快照之后的写入会丢
- ⚠ 恢复后需要重启内核进程（数据库连接持有旧文件句柄）

一句话：**「丢了能救回来」已经做到并有实测；
「永远不会丢」还没做到，需要外部备份策略配合。**

## 项目纪律

1. **一切以实验数据为准** —— 不凭直觉，不凭权威
2. **先测量再动手** —— 性能优化必须先剖析（FTS5 教训）
3. **红线不可动** —— 任何改动跑全量回归
4. **历史不删除** —— 只归档（`archive/`、`archive_legacy/`）
5. **测试写错比代码写错更常见** —— E-28 的 34/34 前先修了 1 个测试断言
6. **戒律优先于功能** —— 不确定是不是破坏红线时，先跑回归再谈
