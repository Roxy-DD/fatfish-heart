## 一、实验设计

**受控合成记忆库**（120 条记忆，155 条图边）：

```
(主体, 关系, 客体) + 自然语言描述 + 话题向量
例：("人003", "负责", "项目017", "人003 负责 项目017", 话题向量)
```

**三类查询**（对应真实场景）：

| 类型 | 例子 | 本质 |
|---|---|---|
| **Q1 单跳** | "人003 负责什么" | 一条记忆里就有 |
| **Q2 两跳** | "人003 所在项目的负责人是谁" | 需要 A→项目→负责人 |
| **Q3 话题** | "那个做记忆系统的" | 无精确词，只能靠语义 |

**五种检索器**：

| 代号 | 机制 |
|---|---|
| V | 扁平向量（话题向量余弦 top-5） |
| K | 关键词（BM25 风格：词命中 + 稀有度加权） |
| G1 | 图 1 跳 |
| G2 | 图 2 跳 |
| H | V + K + G2 的 RRF 融合 |

## 三、四条读出来的结论

### 3.1 Q1 单跳：**五种方式全是 1.0，没有区别**

**→ 单跳事实查询不是区分点。** 任何结构都能做。

### 3.2 Q2 两跳：**只有 G2（图 2 跳）和 K 能到 1.0**

- **V 向量 = 0.0000**：**完全失败**
- G1 图 1 跳 = 0.5：只能走到一半
- **G2 图 2 跳 = 1.0**：走完两跳

**→ 这是图存储唯一不可替代的地方：多跳关系推理。**

**向量检索在这里是 0，不是"差一点"，是完全做不到。**

### 3.3 Q3 话题：**只有 V 能工作（0.5461），其他全是 0**

**K、G1、G2 全部 0.0000。**

**→ 反过来，语义模糊查询只有向量能做。图完全无能为力。**

### 3.4 H 混合：**每一项都取到该类的最高值**

```
Q1: 1.0      Q2: 1.0      Q3: 0.5461
```

**混合不是"折中"，是"每类都用对它最擅长的那个"。**

## 四、必须指出的测试缺陷（不能拿这个当结论）

### 缺陷：Q2 的 K 得 1.0 是**测试泄漏**

Q2 的查询词我给的是 `[项目名, "负责人"]`。

**但真实的问法是「人003 所在项目的负责人是谁」——用户只给人名，不给项目名。**

我给 K 提供了**答案旁边的那个词**（项目名），所以它蒙对了。

**修正后的真实情况**：

| 检索器 | Q2 真实表现 |
|---|---|
| V | 0.0 |
| K | **应该很低**（只有人名，匹配不到"负责人"那条记忆） |
| G2 | **1.0（真的靠跳转）** |

**→ 修掉泄漏后，图的价值会更大，不是更小。**

### 其他边界

| 边界 | 说明 |
|---|---|
| 合成数据 | 不是真实对话，实体/关系是造的 |
| 图规模小 | 155 条边，真实记忆会大几个数量级 |
| 没测延迟 | 只测了召回 |

## 五、回答"为什么不用图存储"

### 5.1 我之前的判断（现在要修正）

我说图"强在关系、弱在部署"。**前半句被证明了**（Q2 只有图能到 1.0），**后半句需要重新评估**。

### 5.2 图在真实记忆里的成本

文献（Zep/Graphiti）的实测代价：

> 每条 episode 需 **3 + N 次 LLM 调用**（N = 抽出的关系数）。
> 5 条关系 → **8 次以上 LLM 调用**。

**但这是"用 LLM 抽关系"的成本，不是"图存储"的成本。**

**如果用规则抽关系（就像我这次实验里 `(主体, 关系, 客体)` 三元组），成本几乎为零。**

### 5.3 所以正确的结论是

> **不是"图好不好"，是"关系从哪来"。**
>
> **LLM 抽关系 → 贵、慢、不确定。**
> **规则/结构抽关系 → 便宜、快、确定，但只适用于有结构的内容。**

## 六、我之前存储方式的真实效果（回答第二个问题）

### 6.1 之前的方案

```
JSON（元数据）+ npz（向量）+ schema 版本号
```

### 6.2 实测效果

| 指标 | 数值 | 出处 |
|---|---|---|
| **跨进程迁移一致率** | **8000/8000 = 100%** | E-4 |
| **余弦偏差** | **0.0** | E-4 |
| 冷启动（10 万条 384 维） | **0.72 s** | E-34 |
| 写入（10 万条） | **6.12 s** | E-34 |
| 磁盘（10 万条 128 维） | 48.95 MB | E-34 |
| 全量扫描 | 1.55 ms（10万） | E-34 |

### 6.3 它的三个硬缺陷

| 缺陷 | 后果 |
|---|---|
| **无全文检索** | 想找"上次提到的那个 DSH"——**只能靠向量，找不到精确词** |
| **无关系结构** | 多跳查询（Q2）**完全做不到** |
| **冷启动慢 5.6×** | 相比 SQLite |

**→ 它证明了"记忆可无损迁移"，但只覆盖了"向量相似"这一种查询。**

## 七、结论：没有单一最优，要按查询类型分层

```
┌──────────────────────────────────────────────┐
│ 真值层（SQLite，WAL）                          │
│   ├─ events   原始对话（只追加）                │
│   ├─ mems     记忆 + 元数据 + 时间              │
│   ├─ triples  (主体,关系,客体) —— 支撑图查询     │
│   ├─ vec      向量 BLOB（int8 量化）            │
│   └─ FTS5     全文索引 —— 支撑关键词             │
├──────────────────────────────────────────────┤
│ 索引层（可丢弃，可从真值层重建）                  │
│   ├─ 邻接表   由 triples 构建 —— 支撑多跳         │
│   └─ 向量矩阵 int8 → float32 载入内存            │
└──────────────────────────────────────────────┘
```

**每种查询走各自的路：**

| 查询 | 走哪条 | 依据 |
|---|---|---|
| 单跳事实 | 任一条 | E-35：五种全 1.0 |
| **多跳关系** | **图遍历** | E-35：**向量 0.0，图 1.0** |
| **模糊话题** | **向量** | E-35：**图 0.0，向量 0.55** |
| 精确实体名 | 全文索引 | 文献：BM25 单路 Recall@5 最高 |
