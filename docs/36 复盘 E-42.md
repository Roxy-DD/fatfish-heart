## 三、10 万条延迟实测

### 3.1 写入侧

```
编码 10 万条: 269 秒（4.5 分钟）
吞吐: 372 条/秒
```

**一次性成本，可接受。**（比 2 万条时的 468 条/秒略低，因为批次调度开销）

### 3.2 查询侧

| 项目 | 耗时 | 说明 |
|---|---|---|
| **编码（单条）** | **45.52 ms** | 每次查询都要 |
| 编码（批 8） | 31.71 ms | 每条 3.96 ms |
| **V 检索 全精度** | **9.12 ms** | float32 512维 × 10万 |
| **V 检索 int8** | **8.41 ms** | 仅快 1.08× |
| **K 检索 FTS5** | **0.044 ms** | 倒排索引 |
| K 检索 numpy | 5.84 ms | FTS5 快 **132.5×** |
| **端到端（缓存未命中）** | **53.98 ms** | |
| **端到端（缓存命中）** | **8.46 ms** | |

### 3.3 关键发现

**① 编码延迟从 6.41 ms 涨到 45.52 ms（10 万条时）**

**这不是"数据变大导致编码变慢"**——编码延迟本应与记忆条数无关。
**原因是**：这次是**独立进程冷启动**后的首次测量，模型未预热，且系统负载不同。

**必须指出这个数据有噪声，需重测确认。**（我在 2 万条实验里测到 6.41ms，这里 45.52ms，差 7 倍，不合理）

**② int8 只快 1.08×，几乎没加速**

**预期 int8 应该快 2–4 倍**（数据量小 4 倍，缓存更友好）。
**实际只快 8%**，说明**瓶颈不是内存带宽，是 numpy 的矩阵乘法实现**。

**→ int8 的真正价值在存储（195 MB → 43 MB），不在速度。**

**③ FTS5 快 132.5×，这是最大单项收益**

```
numpy 全表扫描: 5.84 ms
FTS5 倒排:      0.044 ms
```

**规模越大差距越大**（2 万条时是 5.8×，10 万条时是 132.5×）。

**这验证了"FTS5 是 O(log N)，numpy 是 O(N)"。**

## 四、命中率测试（这个必须诚实说）

| 查询类型 | 命中率 | 说明 |
|---|---|---|
| repeat（完全重复） | **0.0%** | ⚠️ 见下方说明 |
| partial（取前半段） | 50.0% | 因为一半文本前半段相同 |
| paraphrase（换语序） | 0.0% | |
| random（无关查询） | 0.0% | |

### 4.1 必须说清的缺陷

**这个命中率测试的设计是错的。**

我在同一批 200 条查询**内部**统计重复率。但：
- `repeat` 类型我用了 `np.random.choice` 选 200 个**不重复**的索引 → 自然 0% 重复
- `partial` 的 50% 是**文本本身前半段相同**造成的偶然，不是真实缓存行为

**→ 这个数字不能用来判断"缓存有效性"。**

### 4.2 真实的缓存命中率取决于什么

**取决于"用户是否会重复问同一件事"。**

| 场景 | 预期命中率 | 依据 |
|---|---|---|
| 反复问"我的参数是什么" | **高**（接近 100%） | 同一问题同一措辞 |
| 每次阐述方式略有不同 | 中（20–50%） | 需语义缓存而非字符串缓存 |
| 每次问新东西 | **低**（接近 0） | 无重复 |

**→ 字符串哈希缓存只对"完全重复"有效。要覆盖"同义不同词"，需要语义缓存（向量近邻判断）。**
