## 零、总原则

### 红线（任何一步破坏即作废该步）

| 编号 | 底线 | 破坏判据 |
|---|---|---|
| **R1** | 无损迁移 100% | 跨进程/跨库后逐字段、逐向量、逐检索结果不一致 |
| **R2** | 不遗忘 | 任何物理删除；或有效集合外的东西消失 |
| **R3** | 索引可确定性重建 | 重建后检索结果不一致 |
| **R4** | 可塑性 | 出现覆盖式更新，旧值无法溯源 |

### 判断口径

- **不预设门槛**：阈值由实验数据标定，不凭感觉
- **规则能做的交给系统，语义判断交给模型**
- **每个实验必须报四项**：性能指标 / 迁移复验 / 召回未退化 / 是否触碰红线

## 二、P0：多通道熟练度

### 2.1 用户原话（设计依据）

> "门锁密码我根本都不会记……刚开始的时候记一次，有一次忘了，去查一下，
> 查了这两三次之后就记住了。**不是我脑子在每次回忆，而是我手上有惯性了，
> 手就直接随着这种惯性，不需要动脑子就能按出来。**"

> "像妈妈的名字……**这种东西都已经成了惯性了，都不需要我去动脑，它自然就出来了。**
> 比如说，我天天喊我妈妈的名字，但是我很少写。有时候我写她的名字还要想一下怎么写，
> 因为她的名字有生僻字。"

### 2.2 关键洞察（我此前理解错的）

| 我原来的理解 | 用户的实际定义 |
|---|---|
| 固定席位 = 一小批"重要记忆清单" | **固定席位 = 某些通道被反复走通形成的惯性** |
| 记忆是"存了内容" | **熟练 = 某条路径被反复走过** |
| 一个记忆一个熟练度 | **同一件事可以有多个通道，各自独立熟练**（会说≠会写） |

### 2.3 设计

**核心：不是给记忆打分，而是记录"通过哪种方式被访问过多少次"。**

```
通道（channel）类型：
  · recall_by_query    被查询命中（"问他"）
  · recall_by_fixed    作为固定席位直接出现（"不用想就出来"）
  · recall_by_chain    通过链式联想到达（"顺藤摸瓜"）
  · recall_by_merge    被融合时用到（"整理想起来"）

同一记忆在不同通道上的计数是独立的（对应"会说≠会写"）。
```

**熟练度如何影响检索**：
- 高熟练通道 → 检索时更容易被优先
- 但这**不是"重要性分数"**，而是"这条路径走得顺"

### 2.4 实现方案（待实验验证）

**存储**：在 `meta` 表加 `channel:{ep_id}` 记录 JSON：
```json
{"recall_by_query": 12, "recall_by_fixed": 3, "recall_by_chain": 5}
```

**为什么不加新表**：
- `meta` 已是 key-value，够用
- 不加表 → schema 不变 → R1/R3 风险最低

**检索时如何使用（待实验）**：
- 方案 A：熟练度高 → 加分（可能引入偏差）
- 方案 B：熟练度高 → 只在"固定席位"里优先（更贴近"惯性"语义）
- 方案 C：不参与排序，只用于诊断

**必须先测出哪种对，不预设。**

### 2.5 验证清单

| # | 验证什么 | 判据 |
|---|---|---|
| 1 | 计数正确性 | 每次检索后对应通道 +1 |
| 2 | 通道独立性 | 查询命中和链式到达分别计数，互不影响 |
| 3 | **R1 迁移** | 通道计数跨进程/跨库一致 |
| 4 | **R2 不遗忘** | 计数只增不减，无删除 |
| 5 | **R3 可重建** | 清空 meta 后重算，检索结果可复现 |
| 6 | **召回不退化** | 对比启用前后，召回率不低于基线 |
| 7 | 是否真的有用 | A/B 对比三种用法，看哪个提升 |

## 三、P1：情绪共振改模型判断

### 3.1 用户原话

> "触发的时候一般要么是有一种非常相似的情景，要么就是有一种情绪进行了共振"

> "我对情绪的感觉，它可能不是思考出来的，而是就像小脑，它自动处理了。
> 你难过的时候是生理反应，并不是你觉得'我要流泪'，所以你给我流泪。"

### 3.2 当前实现的问题

`store_v1.py` 路 C：
```python
if abs(cur.valence) >= 0.15 and cur.affect_peak >= 0.15:
    if v * cur.valence > 0 and abs(p - cur.affect_peak) <= 0.25:
        cands[eid] += 0.6
```

**问题**（E-142 实测）：
- 中性叙事（"在栈桥吃烤鱿鱼"）的 `affect=0.0`，**永远不共振**
- 阈值 0.15 是拍脑袋的，没有实验依据

### 3.3 设计

**与链式展开相同的模式**：
- 系统：提供候选 + 情绪维度数值（valence/affect）
- 模型：判断"这两条记忆的情绪是否共振"

**但要注意用户说的"情绪是自动的、快速的，不是深思熟虑"** ——
这意味着**用大模型判断情绪可能违背设计意图**（太慢、太"思考"）。

**所以要先实验对比**：
- 方案 A：模型判断（准，但慢）
- 方案 B：改进规则（快，但可能有覆盖问题）
- 方案 C：混合（规则粗筛 + 模型精筛，沿用已验证的两级架构）

### 3.4 验证清单

| # | 验证什么 | 判据 |
|---|---|---|
| 1 | 情绪共振召回率 | 构造有情绪关联的样本，看能否召回 |
| 2 | 中文叙事的覆盖 | 中性但有情绪底色的句子能否识别 |
| 3 | 延迟 | A/B/C 三方案对比 |
| 4 | **R2 不遗忘** | 情绪重算不改原文 |
| 5 | 召回不退化 | 对比启用前后 |

## 四、P2：公开数据集对标

### 4.1 候选数据集（按适配难度排序）

| 数据集 | 测什么 | 适配难度 | 说明 |
|---|---|---|---|
| **LongMemEval** | 长程记忆（含信息更新） | 中 | 有"knowledge update"类别，正好对我们的矛盾处理 |
| **LoCoMo** | 长对话记忆问答 | 中 | 多轮对话，需要把我们的系统接在 LLM 前 |
| **MemBench** | 记忆增删改查 | 中低 | 更接近我们的形态 |
| **Mem0 benchmark** | 检索召回 | 低 | 他们报告 top-200 → 7K token，可直接对照 |

### 4.2 适配方案

**核心问题**：这些数据集都是"对话级"，我们是"事实级"。

**适配思路**：
```
数据集的一条对话
  → 用我们的复盘机制抽出事实 → 写入记忆库
  → 用数据集的问题检索 → 取 top-N
  → 交给 LLM 作答
  → 与标准答案比对
```

**关键：我们不能改数据集，只能改自己的适配层。**

### 4.3 验证清单

| # | 验证什么 | 判据 |
|---|---|---|
| 1 | 能否跑通（不改数据集） | 端到端出结果 |
| 2 | 基线数字 | 与 Mem0/LongMemEval 论文报告对比 |
| 3 | **矛盾处理专项** | 在 knowledge update 类问题上单独报 |
| 4 | 成本 | token / 延迟 |
| 5 | **R1-R4** | 全部复验 |
