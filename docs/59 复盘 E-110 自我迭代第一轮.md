## 一、这轮优化了什么

针对之前审计出的三个 P0 问题：

| # | 问题 | 优化前 | 优化后 | 提升 |
|---|---|---|---|---|
| **1** | 每轮启动新 Python 进程，重载 BGE 模型 | 每次 1500-2000 ms | **13-18 ms**（常驻） | **约 100 倍** |
| **2** | 每轮全量重扫 7000+ 事件日志 | O(n) 全量遍历 | 增量扫描（记录 seq 游标） | 随对话增长不再变慢 |
| **3** | 写入无去重，模型重复记同一件事 | 重复条目累积 | 归一化 hash 去重 | 实测生效 |

## 二、实测数据

### 常驻内核延迟（三次请求）

| 请求 | 延迟 | 说明 |
|---|---|---|
| 请求 1（stats） | 7586 ms | 含预热（模型加载），仅进程启动时一次 |
| 请求 2（search） | **16 ms** | 稳态 |
| 请求 3（search） | **13 ms** | 稳态 |
| 请求 4（search） | **17 ms** | 稳态 |

**稳态延迟 13-18 ms，对比旧方案每次 1500-2000 ms，提升约 100 倍。​**

### 预热的关键教训

第一版预热只创建了 store 对象，**没有真正加载 BGE 模型**，导致第一次 search 依然要 8473 ms。​

修法：预热时必须真的跑一次 `Embedder.get().encode("预热")` + 一次 `search()`。​

**这是"预热必须真的走一遍热路径"的教训。​**

### 去重验证

| 场景 | 结果 |
|---|---|
| 同文本写入 2 次 | ✅ 第 2 次 `deduped=True`，未重复写 |
| 不同文本 | ✅ 正常写入 |
| 仅空格差异 | ✅ 归一化后判定为重复 |
| 最终条数 | 2 条（预期 2 条）✅ |

## 三、架构变化

### 优化前

```
DSH 每轮 → spawn python cli_mcp.py（加载 BGE 1.5s）→ 处理 → 退出
```

### 优化后

```
DSH 首次 → spawn python kernel_server.py（加载 BGE 一次）
           ↓ 保持长连接
       每轮 → 写一行 JSON → 读一行 JSON 响应（13ms）
           ↓
       插件卸载时才关闭
```

**协议**：JSONL，每行一个请求/响应，带 `id` 用于并发匹配。​
