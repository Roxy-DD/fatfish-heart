## 一、先盘点：现在有什么数据可展示

### 1.1 每条记忆（Episode）的字段

| 字段 | 含义 | 展示价值 |
|---|---|---|
| `raw_text` | 记忆原文 | 核心，必须展示 |
| `cost` | 失去代价（0-1） | 高 → 固定席位，最重要 |
| `affect_peak` | 情绪强度（0-1） | 情绪触发 |
| `valence` | 情绪方向（-1~1） | 正/负情绪 |
| `created_at` | 创建时间 | 时间线 |
| `invalid_at` | 失效时间 | 已失效标记 |
| `superseded_by` | 被哪条取代 | 关系链（R2 不遗忘的体现） |
| `revision` | 修订次数 | 可塑性体现 |
| `confidence` | 置信度 | 可靠性 |
| `person/time/location/triggers` | 结构化抽取 | 人物/时间/地点/触发场景 |
| `atmosphere` | 氛围 | 情景记忆的核心（用户定义） |
| `text_hash` | 内容哈希 | R3 可重建 |

### 1.2 派生层（scope_of / issues_of）

| 派生 | 含义 | 展示价值 |
|---|---|---|
| `scope` | 六维能力范围（existence/identity/time_exact/time_range/value/location） | 「这条记忆能回答哪类问题」 |
| `issues` | 缺陷（missing_object 等） | 质量标记 |

### 1.3 全局统计（stats）

| 字段 | 含义 |
|---|---|
| `total/valid/invalid` | 总数/有效/失效 |
| `vectors` | 向量数（索引健康） |
| `high_cost` | 高代价数 |
| `high_affect` | 强情绪数 |
| `size_mb` | 数据库大小 |

### 1.4 当前配置项（cordis.patch.yml）

| 配置 | 含义 |
|---|---|
| `autoInject` / `autoRemember` | 是否自动注入/自动记忆 |
| `autoInjectTopK` / `autoInjectMaxChars` | 注入条数/字符数 |
| `reviewWindow` | 复盘窗口 |
| `reviewProvider` / `reviewModel` | 复盘用的模型 |
| `minImportance` / `minCost` | 记忆门槛 |
| `debugLog` | 调试日志 |

## 二、现状 UI 的问题

读现有 `client.js`，发现这些设计缺陷：

1. **信息密度低**：每条记忆只显示 `raw_text` + 几个 tag，`valence`、`atmosphere`、`triggers`、`revision`、`superseded_by` 这些字段**完全没展示**
2. **没有关系可视化**：R2 的「失效→被取代」链、revision 历史，看不到
3. **没有时间线**：`created_at` 有，但没做时间线视图，只是平铺列表
4. **统计卡片太少**：只有 5 个（总数/有效/失效/高代价/有缺陷），`size_mb`、`vectors`、`high_affect` 没展示
5. **配置零散**：配置只在 cordis.patch.yml 里，UI 没有配置面板
6. **没有检索测试入口**：新增的 `rerank`/`rerank_llm` 精排能力，UI 里没有可视化入口测试
7. **没有情绪可视化**：`valence`（正/负情绪）这个维度完全没用上

---

## 三、重新设计的核心原则

**这个记忆系统的哲学是「情景记忆」**——记忆不只是事实，还有情绪、氛围、代价、时代感。

所以 UI 不能只是"事实列表"，要能**看到记忆的「质感」**：

1. **代价可视化**：高代价记忆要一眼看出"这条丢了会出大事"
2. **情绪可视化**：正负情绪、强度，用颜色/符号表达
3. **关系可视化**：失效→被取代的链，revision 历史
4. **时间线**：记忆随时间的累积，而不是平铺
5. **可检验**：能搜索、能测试精排、能看"这条能答什么"

## 四、UI 布局方案

### 4.1 整体结构：三个 Tab

```
记忆库（主面板）
├── Tab 1: 记忆列表（默认）
├── Tab 2: 时间线
└── Tab 3: 设置/诊断
```

### 4.2 Tab 1: 记忆列表

**顶部统计条**（扩展为 8 个卡片）：
```
总数 | 有效 | 已失效 | 高代价 | 强情绪 | 有缺陷 | 向量数 | 库大小
```

**工具栏**：
```
搜索框 | 排序下拉（时间/代价/情绪/相关性）| 过滤（高代价/强情绪/已失效/正情绪/负情绪）| 精排开关（cross-encoder 测试）
```

**记忆卡片**（重构 MemoryRow，信息密度提升）：
```
┌─────────────────────────────────────────┐
│ 我电脑的登录密码是8848，千万别忘了        │  ← raw_text
│                                          │
│ [高代价] [强情绪] [负向]  #修订2  [已失效]  │  ← 状态 tag
│ 代价 0.90  情绪 0.85  ▼负向              │  ← 双维度进度条
│ 能答：identity/value   缺陷：无           │  ← scope + issues
│ 触发：密码  时间：无  地点：无            │  ← 结构化字段
│ 创建 2026-11-07 14:30 · id abc123 · 被 xyz 取代 │  ← 元信息 + 关系
│ [编辑] [失效] [查看历史]                 │  ← 操作
└─────────────────────────────────────────┘
```

### 4.3 Tab 2: 时间线

按 `created_at` 分组的纵向时间线，每条记忆是一个节点，颜色按 cost 深浅，情绪用图标（😊/😢/中性）。

### 4.4 Tab 3: 设置/诊断

**配置面板**（对应 cordis.patch.yml 的可调项）：
```
自动注入 [开关]     注入条数 [数字]
自动记忆 [开关]     复盘窗口 [数字]
记忆门槛 [滑块]     调试日志 [开关]
复盘模型 [下拉]
```

**诊断区**：
- 检索测试框：输入 query，选精排开关，看结果排序
- 红线自检：迁移/重建/不遗忘 的快速自检按钮
- 数据库大小、向量数

## 五、关键设计决策

### 5.1 「情绪可视化」是这个系统最该有的差异化

现有 UI 完全没展示 `valence` 和 `affect_peak`。但这是用户 docs/49 定义的核心——**情绪是情景记忆的底色**。

**设计**：每条记忆加一个「情绪点」——左侧一条竖色条，正情绪=暖色（橙/红），负情绪=冷色（蓝），强度=深浅，中性=灰。

### 5.2 「关系链」可视化 R2 的价值

R2 不遗忘（只标失效，不删除）是红线。UI 应该让用户**看到**这条红线在起作用：

- 已失效的记忆，显示"被 xxx 取代"的链接
- 点击能跳到取代它的那条
- revision > 1 的显示"修订历史"

### 5.3 「能答什么」比「内容」更关键

`scope`（六维能力范围）是这个系统独特的能力——它回答"这条记忆能回答哪类问题"，而不是"这条记忆是什么事实"。

**设计**：每条记忆显示 scope 徽章，让用户一眼看出"这条是身份信息 / 时间信息 / 数值信息"。

## 六、展示方式的取舍

| 方案 | 优点 | 缺点 | 结论 |
|---|---|---|---|
| 平铺列表（现状） | 简单 | 信息密度低，看不出关系 | 保留为默认，但增强 |
| 卡片网格 | 视觉好 | 长文本溢出 | 不适合记忆文本 |
| **增强列表** | 信息密度可控 | 需精细排版 | ✅ 主方案 |
| 时间线 | 看出累积过程 | 占空间 | ✅ 第二 Tab |
| 图谱（关系可视化） | 直观 | 实现复杂，数据不够稠密 | 暂不做 |
