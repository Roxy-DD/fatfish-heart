## 四、关键边界判断（E-179）★ 最重要

**多跳题不是检索题，是推理题：**

| 题型 | 答案词在证据里的平均覆盖率 |
|---|---|
| 单跳 | **0.673** |
| 多跳 | **0.158** |

**多跳题的答案只有 15.8% 能在证据原文找到，其余需要推理得出。**

**案例：**
```
Q: Would Caroline want to move back to her home country soon?
A: No; she's in the process of adopting children.
证据: "I passed the adoption agency interviews last Friday!"
→ 需要推理链：通过收养面试 → 正在收养 → 不会马上回国
```

**结论：多跳的低分不是检索缺陷，是题目性质。检索只负责"找到素材"。**

## 六、方法论教训（我犯的错）

**连续三轮（E-172 / E-174 / E-176）用手写复现代码做实验，结论全部作废。**

**E-173 验证：手写复现与真实 `store.search` 的 top-10 有 0/5 一致。**

**根因**：真实代码只把语义 top-40 放进打分表，我的复现给所有记忆都算了语义分。

**此后改用「真实代码 + 传参数」或「monkey-patch 真实路径」的方式。**

| 每题最好 evidence 的排名 | 占比 | 累计 |

## 九、最终边界结论

**已经排除的路（7 个实验）：**

| 方法 | 结果 |
|---|---|
| 英文停用词 | ✅ +6.6pp（唯一有效） |
| 英文实体抽取 | ❌ -3pp |
| 结构化通道 | ❌ 有害 |
| IDF 加权 | ❌ +0.2pp |
| 候选池参数 | ❌ +1.21pp |
| 多查询 + RRF | ❌ -6.67pp |
| 席位扩展 | ❌ -2pp |

**共同点：都在改检索层，而瓶颈在 embedding 语义匹配。**

**性能分解：**
```
0.5919（当前）
├─ 纯语义上限     0.5466
├─ 多路融合       +4.53pp
└─ 剩余 33.2% 卡在 embedding 语义距离
```

## 十、碰到边界了（需要用户决策）

**剩余提升只能来自：**

1. **换更强 embedding**（当前 BGE-small-zh 是中文小模型，LoCoMo 是英文语料）
   - 代价：内存↑、启动↑、需要重建全部向量
2. **查询改写**（用 LLM 把问题改成更接近证据的表述）
   - 代价：每次查询多一次模型调用

**这两个都超出"检索层调参"的范围，需要用户定方向。**
