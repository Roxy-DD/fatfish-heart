## 一、三个决定

用户说"这些也由你自主决定，以你现在大模型的能力完全可以做这些判断"。

我按"**判断交给模型，机械交给系统**"这条贯穿全项目的原则定了：

| 问题 | 决定 | 理由 |
|---|---|---|
| ① L3 过时判定 | **(a) 模型主动判断（和 sleep 一起）** | 系统只负责把 L3 候选挑出来打包，判不判、判哪个交给模型 |
| ② sleep 扫描窗口 | **改成"自上次睡眠以来新增"**，并保留兜底 | 纯机械逻辑，属于系统职责 |
| ③ 演化链追溯 | **做** | 纯机械查询，是 R4「可溯源」的完整实现 |

## 二、① L3 过时判定（模型负责）

### 实现

`prepare_sleep_pack` 额外返回 `l3_candidates`：

```json
{
  "l3_candidates": [
    {"ep_id": "...", "text": "...", "age_h": 12.5}
  ]
}
```

只挑 **L3（未标记保护）** 的记忆——L0/L1/L2 永远不进这个列表。

### 模型怎么判

`mem_sleep` 的 prompt 里明确写了判断依据：

```
判断 L3 是否过时的依据（谨慎，宁可留着也别误删）：
  · 内容已被更新的信息取代（如旧的阶段结论已推进）
  · 明确是一次性/临时性的记录，任务已完结
  · 与当前仍有效的记忆直接矛盾
  若只是"时间久了"但内容仍然成立，应当保留。
```

**关键设计**：明确写"宁可留着也别误删"，因为误删的代价高于保留的成本（R2 精神）。

## 三、② 睡眠扫描窗口（系统负责）

### 问题

原实现：

```python
SELECT ... ORDER BY created_at DESC LIMIT 50   # 只看最近 50 条
```

记忆增长到几百条后，**老碎片永远扫不到**，也就永远不被整理。

### 修法：游标式增量

```python
# meta 表存游标
sleep:cursor = 上次睡眠的时间戳

# 增量窗口：上次睡眠之后新增的
SELECT ... WHERE created_at > cursor

# 兜底：首次睡眠 / 增量不足 2 条 → 退回最近 N 条
```

### 语义

| 情况 | window | 说明 |
|---|---|---|
| 首次睡眠（cursor=0） | `"recent"` | 用最近 N 条兜底 |
| 增量 >= 2 条 | `"fresh"` | 只扫新增 |
| 增量 < 2 条 | `"recent"` | 太少，退回兜底 |

`sleep_apply` 完成后自动推进游标（可用 `advance_cursor:false` 关闭）。

## 四、③ 演化链追溯（系统负责）

### 问题

原来只能看到一步：`superseded_by` 指向"被谁取代"。但 A→B→C 的完整链看不到。

### 实现

`consolidate.evolution_chain(st, ep_id)`：

```
双向追溯：
  · 向前：谁取代了当前这条（沿 superseded_by 走）
  · 向后：当前这条取代了谁（反向查）
  · 组装成从老到新的完整链
```

返回：

```json
{
  "root": "最老的一条",
  "tip":  "最新的一条",
  "length": 3,
  "chain": [
    {"ep_id":"...", "text":"...", "is_current":false, "revision":1},
    {"ep_id":"...", "text":"...", "is_current":false, "revision":1},
    {"ep_id":"...", "text":"...", "is_current":true,  "revision":1}
  ]
}
```

### 特点

- **从链上任意一条都能拿到完整链**（头/中/尾都测过）
- 纯机械查询，无判断成分
- `is_current` 直接标明哪条是当前有效版本

### 插件工具

`mem_trace`——模型想知道"这个信息历史上改过几次、最新是什么"时调用。

## 六、发现并修正的一个测试 bug

E-29 首轮 18/19，失败项："首次睡眠走兜底窗口"。

**根因**：`cursor=0` 时 `created_at > 0` 把所有记忆都当成"新增"，导致 window 误报为 `"fresh"`。

**这不是测试错，是代码逻辑不严谨**——首次睡眠在语义上不是"增量"。
修法：显式判断 `cursor > 0` 才走增量窗口。

## 七、另一个"假警报"

种子验证曾从 27/27 掉到 26/27，报"有效记忆 = 12 条，实际 14"。

**真相**：多的 2 条是插件自动记忆**真实写入的**用户记忆
（记录了"用户希望模型自主判断设计细节"这件事），不是测试污染。

**这是系统正常工作的证据**，反而是好事。

修法：验证脚本改为「种子 12 条全部有效」+「有效记忆 >= 种子数」
+ 隐私扫描只扫**种子记忆**（用户自己的记忆当然可以含私人内容）。

## 八、更新后的生命周期全貌

```
① 写入 (add)
    ↓
② 活跃 (invalid_at = NULL)
    ├─ 被检索、被注入、被强化
    ├─ revise → revision+1
    └─ 可能被 trace 追溯（A→B→C）
    ↓
③ 睡眠整理（模型主动触发）
    ├─ 扫增量窗口（自上次睡眠以来新增）
    ├─ 判相似对：merge 碎片 / keep 不动
    ├─ 判 L3 候选：是否已过时 → invalidate
    └─ 推进游标
    ↓
④ 退出（三条路，全部只打标记）
    ├─ invalidate
    ├─ supersede
    └─ sleep invalidate（含 L3 退役）
    ↓
⑤ 失效 (invalid_at ≠ NULL) —— 数据永久保留
    └─ 可经 trace 追溯完整演化链
```
