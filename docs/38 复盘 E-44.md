## 二、三个关键结论

### 2.1 HNSW 是明确的赢家

```
EXACT:      4.325 ms, Recall 1.000
HNSW ef=32: 0.096 ms, Recall 0.960   → 加速 45.1×，召回掉 4pp
HNSW ef=64: 0.153 ms, Recall 0.962   → 加速 28.3×，召回掉 3.8pp
```

**用 4 个百分点的召回，换 45 倍速度。**

**如果召回要紧，ef=64 更稳（3.8pp 换 28×）。**

### 2.2 我自己实现的 IVF 有 bug

```
我的 IVF np=8:  1.797 ms, Recall 0.848
FAISS-IVF np=8: 0.225 ms, Recall 0.856
```

**召回差不多（0.848 vs 0.856），但慢了 8 倍。**

**原因**：我的实现每次都 `np.concatenate` 候选列表再重新算 `M[cand] @ qv`，
这会产生大量内存拷贝。FAISS 用连续存储 + 预计算，避免了这个开销。

**→ 结论：能用 FAISS 就用 FAISS，自己实现只有教学价值。**

### 2.3 IVF-PQ 在我这里彻底失败

```
IVF-PQ np=8:  延迟 0.387 ms（最快！）Recall 0.3820（惨）
```

**Recall 只有 38%，完全不可用。**

**原因**：我只用了 16 段 × 256 码字，且**没有做 re-rank**。
文献里 PQ 必须配"近似粗筛 + 全精度重排"才可用。

**→ 这是实现缺失，不是方法不行。但我没时间补了，先记录。**

| **5** | 没测 HNSW 在 100 万条的表现 | 规模外推未验证 |

### 第 4 条要特别说

**HNSW 的内存 143 MB 是"全精度向量 + 图"**，而我们的真值层是 36 MB（int8）。

**这意味着：如果上 HNSW，内存要为它单独付 4 倍。**

**折中方案：HNSW 建在 int8 上（FAISS 支持），内存能降到 ~50 MB。需验证召回。**
