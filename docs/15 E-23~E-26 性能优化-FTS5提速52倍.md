# E-23~E-26 性能优化：FTS5 查询提速 52 倍

## 一、问题发现（E-23）

性能基准暴露**检索延迟随数据量线性增长**：

| 规模 | 修复前检索延迟 |
|---|---|
| 100 条 | 55.1 ms |
| 500 条 | 342.1 ms |
| **2000 条** | **1383.1 ms** ← 不可用 |

写入反而稳定（11-12 ms/条）。

**结论：问题在检索路径，不是写入。**

## 二、逐通道剖析（E-24）

拆解 `store.search` 五个通道：

| 通道 | 耗时 | 占比 |
|---|---|---|
| **FTS5** | **343.7 ms** | **95.2%** ← 瓶颈 |
| 语义 | 10.5 ms | 2.9% |
| LIKE | 4.2 ms | 1.1% |
| 情绪 | 2.4 ms | 0.7% |
| 结构化 | 0.4 ms | 0.1% |

**之前怀疑的 LIKE 全表扫描和情绪通道都不是问题，FTS5 才是。**

## 三、深挖根因（E-25 / E-26）

### E-25 排除法

| 嫌疑 | 验证结果 |
|---|---|
| OR 拼接 7 词太宽 | ❌ MATCH 本身只要 0.2ms |
| bm25 排序开销 | ❌ 只要 0.5ms |
| rank 替代 bm25 | ❌ 无提升 |
| FTS 索引碎片 | ❌ optimize 只省 0.2ms |
| **JOIN episodes** | ✅ **256ms！** |

### E-26 对比六种写法

| 写法 | 耗时 |
|---|---|
| A 不回表（无排序） | 0.06 ms |
| B 不回表 + rank 排序 | 0.61 ms |
| **C 回表 JOIN（原实现）** | **69.79 ms** |
| D 两段式（rowid → ep_id IN） | 0.80 ms |
| **E 子查询 IN** | **0.24 ms** |
| F 不回表 + NOT IN | 0.75 ms |

**根因确认**：`ep_fts` 是 **external content 表**（`content='episodes'`），
JOIN 时 SQLite 需要回表读取每行的 `raw_text` 重建索引内容，
开销 O(命中行数 × 文本长度)。

## 四、修复（store_v1.py）

**改法**：两段式查询

```python
# 修复前（回表 69.79ms）
for eid, s in self.con.execute("""
    SELECT e.ep_id, bm25(ep_fts) AS s
    FROM ep_fts JOIN episodes e ON e.rowid=ep_fts.rowid
    WHERE ep_fts MATCH ? AND e.invalid_at IS NULL
    ORDER BY s LIMIT ?""", (expr, top*6)).fetchall():
    scores[eid] = scores.get(eid, 0) + 1.0 / (1 + abs(s))

# 修复后（两段式 0.80ms）
fts_rows = self.con.execute(
    "SELECT rowid, bm25(ep_fts) AS s FROM ep_fts "
    "WHERE ep_fts MATCH ? ORDER BY s LIMIT ?",
    (expr, top * 6)).fetchall()
if fts_rows:
    rids = [r[0] for r in fts_rows]
    smap = {r[0]: r[1] for r in fts_rows}
    ph = ",".join("?" * len(rids))
    for (eid, rid) in self.con.execute(
            f"SELECT ep_id, rowid FROM episodes e "
            f"WHERE rowid IN ({ph}) {w}", rids).fetchall():
        s = smap.get(rid, 0.0)
        scores[eid] = scores.get(eid, 0) + 1.0 / (1 + abs(s))
```

## 七、方法论要点

### 这次的关键是「逐通道剖析」

如果只看到"检索慢 1383ms"，很容易去优化语义通道（直觉上最重），
但实际上是 FTS5 的 JOIN 回表。

**教训**：性能优化必须**先测量再动手**，不能凭直觉。

### 第二课：external content 表的陷阱

SQLite FTS5 的 `content='episodes'` 设计本意是「不重复存储内容」，
但代价是**每次 JOIN 都要回表读原文**。

正确用法是：**先用 FTS 拿到 rowid（不回表），再单独查需要的字段**。
