# 回馈机制：环 → 群的横向边

> 这份文档说明「一个独立实例怎么把自己的演化成果送回上游」，
> 以及为什么这一步**不需要使用者懂 Git**。

---

## 为什么需要这个机制

《环管群》主张 4：

> 演化关系不必是单一树状链。多个谱系可以交换机制、经验与结构，
> 并通过交叉重组形成新的分支。

但常规开源流程把这条路卡死在了人的能力上：

```
有想法 → 会改代码 → 懂 Git → 会提 PR → 才能贡献
```

任何一环缺失，这个实例的演化成果就**死在本地**，回不到群。
谱系因此变成一条条孤立的死枝。

**这个机制要拆掉的就是"懂 Git"这一环。**

---

## 三层设计

### 层 1：发现（自动）

系统自己扫描本地相对上游的差异，分类成：

| 类别 | 含义 | 处理 |
|---|---|---|
| **可贡献** | 代码、文档、测试 | 候选 |
| **禁止上传** | 数据库、备份、密钥 | 永不 |
| **实验产物** | `results/*.json` | 不计入贡献 |

```bash
python proto/onward.py
```

输出候选清单 + 安全检查结果，**不推送任何东西**。

### 层 2：询问（必须经过）

```
这些改动要上传到公共仓库，属于外部提交。
必须由用户明确同意后才能执行层 3。
```

这一步**不可自动化**。原因不是技术限制，而是：

> 把别人机器上的东西传到公共空间，必须由那个人决定。

系统能做的是把决策所需信息准备好：

- 改了哪些文件
- 安全检查过没过
- 这些改动对别人有没有用（不是对你自己）

### 层 3：执行（授权后自动）

```bash
python proto/onward.py --push
```

自动完成：建分支 → 提交 → 推送 → 开 PR。

**三重门禁，任何一道不过就拒绝执行：**

1. 安全检查未通过 → 拒绝
2. 没有可贡献改动 → 拒绝
3. 改动全是实验产物 → 拒绝

---

## 自动执行的安全边界

这个机制会往公共仓库写东西，所以边界必须写死：

| 边界 | 实现 |
|---|---|
| 绝不上传数据库 | 路径正则拦截 `.db` / `.backup` / `.seed.json` |
| 绝不上传本机路径 | 扫描 `C:\Users\xxx\` 并阻断 |
| 绝不推 master | 只推 `onward/<时间戳>` 分支 |
| 绝不 force push | 命令里不含 `--force` |
| 绝不无授权推送 | 无 `--push` 参数时只发现 |
| PR 必须可审查 | 描述里列出所有改动 + 安全检查结果 |

---

## 为什么 PR 不能自动合并

最后一公里留给人类，是有意的：

> **「这个改动对群体是否真的更好」是判断题，
> 不该由提交方自己裁决。**

《环管群》主张 5 说环境不是内部评分器。
如果提交方自己决定合并，那就是用内部判断替代环境筛选 —— 正是这条主张禁止的。

审查者要看的不是"代码写得对不对"，而是：

- 这个改动是**提升通用性**，还是**这个实例的特殊配置**？
- 它会不会让别人的实例变差？
- 它的收益是普遍的，还是偶然的？

---

## 对使用者的意义

| 不需要 | 需要 |
|---|---|
| 会 Git | 判断「这次改进值得分享吗」 |
| 会写代码 | 判断「它对别人有用吗」 |
| 懂 PR 流程 | —— |
| 有 GitHub 账号（系统可代持） | —— |

**贡献的门槛从"技术能力"降到"经验判断"。**

这才符合主张 4 的意图：横向的边不该只属于少数人。

### 未做的部分及原因

**「部署后 AI 自动建议用户要不要上传」** 还没做。

技术上可以做（在 `mem_sleep` 或会话结束时检查一次），但现在的判断是：

1. 上游还没有外部贡献者，机制空转没有意义
2. 触发时机需要实验数据（每次会话？每次提交？每周？）—— 拍脑袋定会变成打扰
3. 先让人手动跑一次，看真实反馈再决定自动化程度

这符合项目纪律：**不预设门槛，遇到了什么问题再看什么会造成效果变差或变好。**
