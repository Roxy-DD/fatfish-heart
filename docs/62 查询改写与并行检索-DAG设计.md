## 零、设计目标

**问题**：E-183 实测，33.2% 的题在 embedding 空间里查不到证据。

**但 E-184/E-185 推翻了"换 embedding"的方向：**
- 所有证据余弦 ≥0.4（中位 0.6683）→ 语义匹配够用
- 证据排在 11-30 名的题，与第 10 名余弦差距 98.3% ≤0.03 → **是排序精度问题，不是语义问题**

**E-186b 决定性结果：LLM 精排救回 49/54 = 90.7%，整体 +16.2pp（0.3775 → 0.5397）**

**→ 正确方向是「精排（rerank）」，不是「换 embedding」或「查询改写」**

---

## 零·五、精排的完整结论（E-184~E-194）★ 决定性

| 实验 | 结论 |
|---|---|
| E-184 | 余弦全 ≥0.4，中位 0.67 → embedding 够用，别换 |
| E-185 | 98.3% 的证据与第 10 名差距 ≤0.03 → 排序分不开 |
| E-186b | 逐条精排救回 90.7%，但成本高（每题 30 次判断） |
| **E-191** | **批量精排命中 99%，优于逐条（90.7%），成本降到 1 次/题** |
| E-194 | **全量精排 +12.2pp（0.5802 → 0.7021）** |

**精排流程（已确认可落地）**：
```
向量检索 top-50（10ms）
    ↓
LLM 批量精排（一次看 50 条，横向比较，~800ms）
    ↓
取 top-10
```

**关键教训**：
- 逐条判断（isolated）反而不如批量（comparative），因为横向比较能区分"都相关但哪个更贴切"
- `top` 参数同时控制"候选池"和"返回条数"，E-189 用 top=50 判基线导致 0.3300（错误），
  正确基线必须用独立 top=10 判（E-194 的 0.5802）
- 粗筛不可行：E-190 证明余弦/关键词在证据与噪声上严重重叠，便宜信号分不开

---

**两个可选方向**：
1. 换更强的 embedding（Qwen3-Embedding-0.6B，MMTEB 64.34 vs 当前 bge-small-zh 未上榜）
2. 查询改写（LLM 把问题改写成更接近证据的表述）

**本设计覆盖方向 2，采用 DAG + 并行。**

## 一、为什么是 DAG 而不是线性流水线

**线性**：
```
改写 → 检索 → 融合 → 返回
  ↑ 串行，每步等上一步
```

**DAG（并行）**：
```
        ┌─ 改写1 ─┐
问题 ───┼─ 改写2 ─┼─→ 各路检索（并行）─→ 融合 ─→ 返回
        └─ 改写3 ─┘
```

**关键收益**：
- 3 个改写并行 → 延迟 ≈ 1 个改写（不是 3 个）
- 各路检索并行 → 延迟 ≈ 1 路
- **总延迟 ≈ max(改写) + max(检索)**，而非串行求和

## 二、完整 DAG

```
                    ┌──────────────────────────────────────┐
                    │          Stage 0: 输入                │
                    │  query（用户问题）                    │
                    │  memories（记忆库，已加载向量矩阵）    │
                    └───────────────┬──────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────┐
                    │      Stage 1: 原查询直接检索（同步）   │
                    │  不等待改写，先拿一个基线结果          │
                    │  延迟：~10ms                          │
                    └───────────────┬──────────────────────┘
                                    │ baseline_result
        ┌───────────────────────────┼───────────────────────────┐
        │                           │                           │
┌───────▼────────┐      ┌───────────▼──────────┐    ┌──────────▼─────────┐
│ Stage 2a       │      │ Stage 2b             │    │ Stage 2c           │
│ 实体聚焦改写    │      │ 时间/条件展开改写     │    │ 同义/上位词改写      │
│ (子智能体并行)  │      │ (子智能体并行)        │    │ (子智能体并行)      │
│                │      │                      │    │                    │
│ 输入: query    │      │ 输入: query          │    │ 输入: query        │
│ 输出: 3-5变体  │      │ 输出: 2-3变体        │    │ 输出: 2-3变体      │
└───────┬────────┘      └───────────┬──────────┘    └──────────┬─────────┘
        │                           │                           │
        └───────────────────────────┼───────────────────────────┘
                                    │ variants (合并、去重)
                    ┌───────────────▼──────────────────────┐
                    │      Stage 3: 多路检索（并行）        │
                    │  每个变体 → 向量检索 top-K            │
                    │  全部并行，不互相等待                 │
                    │  延迟：~10ms（不是 N×10ms）           │
                    └───────────────┬──────────────────────┘
                                    │ ranked_lists[]
                    ┌───────────────▼──────────────────────┐
                    │      Stage 4: 融合                    │
                    │  RRF（只看名次，不看分数尺度）         │
                    │  或加权分数融合                        │
                    └───────────────┬──────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────┐
                    │      Stage 5: 裁决（可选，模型）      │
                    │  候选太多时，让模型判断哪条最相关      │
                    │  只在 top-30 里做，不重算向量         │
                    └───────────────┬──────────────────────┘
                                    │
                    ┌───────────────▼──────────────────────┐
                    │      Stage 6: 输出                    │
                    │  top-K 记忆 + 每条的来源标记          │
                    └──────────────────────────────────────┘
```

## 三、状态机（阶段切换条件）

```
IDLE
  │ query 到达
  ▼
BASELINE_RUNNING ──(完成)──→ BASELINE_READY
  │                              │
  │ (同时启动改写)                │
  ▼                              │
REWRITE_FANNING_OUT              │
  │                              │
  ├─ 任一改写完成 → 立即检索该变体 │
  │                              │
  ▼                              │
RETRIEVE_FANNING_OUT             │
  │                              │
  ├─ 全部检索完成 ──────────────┐ │
  │                             │ │
  ▼                             ▼ ▼
FUSING ←──────────────────── BASELINE_READY
  │
  ▼
ARBITRATING（仅当候选 > 阈值）
  │
  ▼
DONE
```

**关键：`BASELINE_RUNNING` 与 `REWRITE_FANNING_OUT` 并行，不串行等待。**

## 四、每个阶段的技术细节

### Stage 1：原查询检索（必须最先跑）

**理由**：改写可能失败或跑偏，原查询是保底信号。
**耗时**：~10ms（现有 store.search）

### Stage 2：改写（3 个子智能体并行）

| 智能体 | 职责 | 输出 |
|---|---|---|
| **A 实体聚焦** | 抽问题里的实体，生成"只问这个实体"的短查询 | 3-5 变体 |
| **B 时间/条件展开** | 把"什么时候/多久/为什么"展开成具体表述 | 2-3 变体 |
| **C 同义/上位词** | 换词、上溯到更宽的概念 | 2-3 变体 |

**并行方式**：三个子智能体同时启动，互不等待。

**预期耗时**：每个 ~800ms，并行后 ≈ 800ms。

### Stage 3：多路检索（并行）

**每个变体独立向量检索**，全部用 numpy 矩阵乘法，可以批量：
```python
# 一次性算所有变体的向量
V = emb.encode(all_variants)        # (n_variants, 512)
S = V @ vec_matrix.T                # (n_variants, n_memories)
# 每行取 top-K
```
**耗时 ≈ 一次检索（10ms），不是 N 次。**

### Stage 4：融合

**RRF 公式**：
```
score(d) = Σ_i  1 / (k + rank_i(d))     k=60
```

**E-181 失败的教训**：
- 机械生成的变体质量差（实词串联丢了语序）
- **这次必须用 LLM 生成的语义改写，不是机械变换**

### Stage 5：裁决（可选）

**只在候选 > 30 时触发**，让模型从 30 条里挑 10 条。

**成本**：一次 LLM 调用（~800ms），但只在必要时。

## 五、延迟预算

| 阶段 | 串行方案 | DAG 方案 |
|---|---|---|
| 原查询检索 | 10ms | **10ms**（并行） |
| 改写（3 个） | 3 × 800 = 2400ms | **800ms**（并行） |
| 多路检索 | 6 × 10 = 60ms | **10ms**（批量） |
| 融合 | 5ms | 5ms |
| 裁决 | 800ms | 800ms（可选） |
| **总计** | **3275ms** | **~825ms**（无裁决）/ **1625ms**（有裁决） |

**DAG 方案比串行快 4 倍。**

## 七、风险与红线

| 风险 | 应对 |
|---|---|
| 改写引入语义漂移 | 保留原查询结果（Stage 1 保底） |
| 并行导致资源竞争 | 子智能体互不共享状态 |
| **R1 迁移** | 改写是查询时的临时计算，不影响存储 |
| **R2 不遗忘** | 只读不写 |
| **R3 可重建** | 改写结果不落盘，可重算 |
| 换 embedding 破坏 R1 | **需要重建全部向量 → 必须先验证 R1/R3** |
